# NGINX Location Block Map

This document describes every URL path prefix and subdomain handled by the `nginx-proxy` container, where each proxies to, any special settings, and the reason for those settings.

The active configuration lives in [nginx/conf.d/prod.conf](../nginx/conf.d/prod.conf) (`mitchellnet.local` and `vault.mitchellnet.local` virtual hosts) and [nginx/conf.d/000-bareip.conf](../nginx/conf.d/000-bareip.conf) (`192.168.2.10` bare-IP virtual host).

---

## Bare-IP Parity Standard

**All services exposed as a `location /path/` under `prod.conf` must be reachable identically via both `https://mitchellnet.local/path/` and `https://192.168.2.10/path/`.** This is enforced going forward by the `aaNewService` checklist (`mitchellnet-infra/scripts/aaNewService`), which explicitly prompts for both vhosts when scaffolding a new service.

**Exemption — subdomain-based services:** Services exposed as their own subdomain rather than a path (currently only **Vaultwarden**, at `vault.mitchellnet.local`) are exempt from this standard. A subdomain is matched by NGINX via the `Host` header / SNI; there is no bare-IP equivalent of a subdomain, so "bare-IP parity" isn't a coherent requirement for these. A future subdomain-based service that also needs bare-IP access would require a deliberate design decision (e.g. exposing it at a path under the bare-IP vhost instead), not an automatic mirror.

**Current state (verified 20 June 2026):** `prod.conf`'s path-based locations and `000-bareip.conf` are in exact parity — see the two tables below.

**TLS certificate:** the self-signed cert used by all vhosts (generated by `mitchellnet-infra/ssl/generate.sh`) includes `192.168.2.10` as a Subject Alternative Name alongside `mitchellnet.local`, `*.mitchellnet.local`, `localhost`, and `127.0.0.1`, added 20 June 2026. See `mitchellnet-infra/docs/runbook.md` § SSL Certificate Renewal for the full generate → deploy lifecycle.

## Common Elements — Both Vhost Files

Every `location {}` block in both `prod.conf` and `000-bareip.conf` includes:

```nginx
include conf.d/security-headers.conf;
```

This applies a shared set of security-related response headers (defined once in `nginx/conf.d/security-headers.conf`) to every proxied response.

Both vhost `server {}` blocks also set these headers at the top level, inherited by every `location {}`:

```nginx
proxy_set_header Host              $host;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

## prod.conf — `mitchellnet.local` virtual host

### `location /api/bench/`

```nginx
location /api/bench/ {
    include conf.d/security-headers.conf;
    proxy_pass http://bench-instrument-service:8000/;
    proxy_http_version 1.1;
    proxy_read_timeout 120s;
    proxy_send_timeout 120s;
    add_header X-Upstream bench-instrument-service;
}
```

| Setting | Value | Reason |
|---------|-------|--------|
| **Upstream** | `bench-instrument-service:8000` | Bench Instrument Service container, resolved by Docker DNS via the `mitchellnet` external network |
| `proxy_read_timeout 120s` | 120 seconds | BIS operations (waveform capture, multimeter logging) can take many seconds; the default 60 s timeout caused premature disconnects |
| `proxy_send_timeout 120s` | 120 seconds | Paired with read timeout to keep the upstream connection alive for slow POST payloads from the client |
| `proxy_http_version 1.1` | HTTP/1.1 | Enables keep-alive connections to the upstream |

> **Why 120 s?** Waveform captures and continuous multimeter logging sessions hold the connection open while data streams from bench hardware. The default 60 s read timeout was insufficient and caused clients to receive a 504 Gateway Timeout mid-capture.

### `location = /version.json`

```nginx
location = /version.json {
    deny all;
    return 404;
}
```

| Setting | Value | Reason |
|---------|-------|--------|
| **Match type** | Exact (`=`) | Only blocks the literal `/version.json` path, not anything under it |
| `deny all; return 404;` | — | Prevents external access to deployment metadata written by the CI deploy workflow |

---

### `location /`

```nginx
location / {
    include conf.d/security-headers.conf;
    ssi on;
    proxy_set_header Accept-Encoding "";
    proxy_pass http://nginx-prod;
    add_header X-Upstream production;
}
```

| Setting | Value | Reason |
|---------|-------|--------|
| **Upstream** | `nginx-prod` (port 80) | Static content container serving HTML/CSS/JS from `html/prod/` |
| `ssi on` | enabled | Server-Side Includes are used to inject shared header/footer fragments into pages |
| `Accept-Encoding ""` | disabled | Prevents upstream gzip compression so NGINX's SSI parser can read and process the HTML before sending it to the client |

---

### `location /includes/`

```nginx
location /includes/ {
    include conf.d/security-headers.conf;
    alias /home/andrew/web_server/includes/;
    autoindex off;
    add_header Cache-Control "no-store";
}
```

| Setting | Value | Reason |
|---------|-------|--------|
| **Served from** | Host filesystem (`./includes/` volume-mounted into the proxy container) | SSI fragments (shared header, footer, nav) are stored here and served directly by the proxy rather than a backend |
| `autoindex off` | disabled | Directory listing hidden for security |
| `Cache-Control: no-store` | no caching | Ensures browsers and proxies always fetch the latest fragment version |

---

### Ordering note

`/api/bench/` is declared before any block that could otherwise shadow it under longest-prefix matching. As of 20 June 2026 there is no longer a generic `/api/` block in `prod.conf` (it was superseded by `/fitness/` when the fitness tracker backend was containerized separately), so this is now a non-issue in practice — but new location blocks should still be added with matching-order in mind if a broader prefix is ever introduced.

## vault.mitchellnet.local — Vaultwarden subdomain virtual host

```nginx
server {
    listen 443 ssl;
    server_name vault.mitchellnet.local;

    ssl_certificate     /etc/nginx/ssl/server.crt;
    ssl_certificate_key /etc/nginx/ssl/server.key;
    include conf.d/ssl-params.conf;

    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    location / {
        include conf.d/security-headers.conf;
        proxy_pass http://vaultwarden:80/;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        add_header X-Upstream vaultwarden;
    }
}
```

| Setting | Value | Reason |
|---------|-------|--------|
| **Type** | Separate `server {}` block, own `server_name` | Vaultwarden is addressed by subdomain, not by path under `mitchellnet.local` |
| **Upstream** | `vaultwarden:80` | Vaultwarden container |
| `proxy_set_header Upgrade` / `Connection "upgrade"` | — | Vaultwarden uses WebSocket connections for live sync; these headers allow the protocol upgrade through the proxy |

> **Bare-IP exemption:** see **Bare-IP Parity Standard** above — this service is intentionally not mirrored on `000-bareip.conf`.

## Network Dependencies

`bench-instrument-service`, `fitness-tracker`, and `recipes-app` are resolved by Docker DNS. The `nginx-proxy` container must be on the `mitchellnet` external Docker network for these names to resolve — see [README.md § 12 Network](../README.md#12-network).

`nginx-prod` is resolved on the `webnet` internal network defined in `docker-compose.yml`.

## Flask Service Routing Patterns

These patterns apply to any Flask-based service proxied through this NGINX setup. They were established during the recipes app build (June 2026).

### Approach A — Trailing Slash Strips the Prefix

Adding a trailing slash to `proxy_pass` causes NGINX to strip the location prefix before forwarding to Flask. Flask routes are then written without the prefix:

```nginx
location /recipes/ {
    proxy_pass http://recipes-app:5000/;  # trailing slash strips /recipes
}
```

```python
@app.route("/")           # handles /recipes/
@app.route("/<int:id>")   # handles /recipes/<id>
```

### Multi-Prefix Exception

Secondary prefixes under the same service (e.g. `/recipes/api/`, or `/meal-plan/` and `/shopping-list/` as used by the recipes app) must use `proxy_pass` **without** a trailing slash so the full path is preserved and Flask can match it:

```nginx
location /recipes/api/ {
    proxy_pass http://recipes-app:5000;  # no trailing slash — preserves /recipes/api/
}
```

### Flask `url_for()` is Prefix-Unaware

`url_for()` generates paths relative to Flask's own routing and does not know about the prefix NGINX adds. Never use `url_for()` for redirects in prefix-routed apps — use hard-coded absolute paths instead:

```python
# Wrong — generates /1, not /recipes/1
return redirect(url_for("recipe_detail", id=r.id))

# Correct
return redirect(f"/recipes/{r.id}")
```

### Templates Must Use HTML Anchor Tags

Jinja2 templates must use HTML `<a>` tags for links. Markdown-style links are not rendered by Flask/Jinja2:

```html
<!-- Correct -->
<a href="/recipes/{{ recipe.id }}">View Recipe</a>

<!-- Wrong — renders as literal text -->
[View Recipe](/recipes/{{ recipe.id }})
```
